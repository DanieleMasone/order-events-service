Project Summary

The service exposes one focused workflow: create an order, persist it, publish an `OrderCreatedEvent`, consume that event, and record idempotent processing. The architecture stays intentionally small while still showing the reliability concerns that matter in real event-driven systems.

API boundary

Validated REST input and stable response DTOs keep the HTTP contract separate from persistence and Kafka payloads.

Event boundary

Kafka producer and consumer code live behind application and infrastructure boundaries with explicit retry behavior.

Data boundary

Flyway owns schema creation, JPA persists orders, and a dedicated table tracks processed event identifiers.

Architecture

The runtime flow is deliberately direct so the transactional and messaging responsibilities are easy to inspect.

Runtime Flow

  1. The client posts a validated create-order request to `/api/orders`.

  2. The service creates the order, persists it through JPA, and flushes the row to PostgreSQL.

  3. The producer publishes `OrderCreatedEvent` to `order.created.v1` using the event ID as the Kafka key.

  4. The consumer receives the event, checks `processed_events`, records the event ID, and returns successfully.

  5. Spring Kafka commits the offset only after the listener completes without an exception.

Idempotency, Retry, and DLT

Idempotency strategy

Each event carries a unique `eventId`. The consumer skips events already present in `processed_events`, which makes duplicate Kafka deliveries safe for this workflow.

Retry and DLT strategy

Transient listener failures are retried with fixed backoff. Exhausted records are published to `order.created.v1.dlt` for inspection or manual replay.

Future Improvements

Transactional outbox

Move broker publication behind an outbox relay when stronger database-to-Kafka consistency is required.

Schema governance

Add schema registry and Avro or Protobuf after the event contract needs independent version governance.

Observability

Add tracing, metrics dashboards, and replay tooling when operating multiple services or consumers.
